# Product Prototype Designer

Объедини product management, бизнес-анализ, UX/UI и React-реализацию в проверяемый пользовательский результат. Это проектный workflow KAPGEO; специализированные skills подключай только для нужной части задачи.

## Контекст и масштаб

1. Работай из корня репозитория. Прочитай `AGENTS.md`, `docs/README.md`, product brief и текущий implementation status; уже прочитанное повторно не загружай без причины.
2. По указателю в `docs/README.md` выбери документы затронутых ролей, экранов, flows и модуля. Найди route, UI-примитивы, семантические токены, repository и соответствующие тесты. Исключай `archive/` из поиска; действуют точные условия доступа из AGENTS.md.
3. Установи границы: БГД, скрытая автономная интерпретация, справочники, заглушка или отдельный Knowledge Map. Не смешивай их данные, правила ревизий и возможности.
4. Маленькое изменение выполняй непосредственно, сохранив контекст и проверив результат. Остальные шаги разворачивай только для существенного UX/продуктового решения.

## Сформулировать пользовательский результат

Опиши кратко: пользователь и его задача → исходный контекст/permission/scope/статус → действие → ожидаемый наблюдаемый результат → следующий шаг.

Укажи необходимые объекты и данные, что было до действия, какие панели/выборы/итоги зависят от него, что должно сохраниться при возврате и reload. Рассмотри исключения, влияние на соседние модули и реалистичность будущей реализации.

Отдели подтверждённые требования (со ссылкой на документ или указание пользователя), фактическое текущее поведение, предложенные решения, допущения, вопросы и будущие технические ограничения. Не называй вывод из кода утверждённым бизнес-правилом. Противоречие сначала сверяй с новейшим записанным решением, затем фиксируй нерешённое в traceability/open questions.

## Спроектировать связный flow

- Построй цепочку вход → выбор объекта → просмотр/редактирование → валидация → сохранение/отмена → обратная связь → возврат. Включи ветви ошибок, отсутствие данных, отказ доступа, read-only, несохранённый черновик и повтор действия, где это имеет смысл.
- Проверь информационную архитектуру: принадлежность экранов, названия, уровни навигации, deep link и Back/Forward; не создавай дубликат существующего рабочего места.
- Если альтернативы существенно меняют усилия пользователя, связность модулей или будущую реализацию, сравни несколько вариантов и выбери обоснованный в пределах запроса. Рутинные решения принимай самостоятельно. Блокирующий вопрос задавай только при недостатке сведений, продолжая независимую работу.
- Для спецификации подключи `pm-product-spec`; для навигации/структуры — `ux-navigation` или `ux-information-architecture-audit`; для таблиц/сводок — `ux-tables` или `ux-dashboard`.

## Реализовать vertical slice

Используй React/strict TypeScript, существующие Router/Query, компоненты и repository; соблюдай направление зависимостей из AGENTS.md. Предложение должно завершаться демонстрируемым исходом, включая согласованные mock-записи и обратную связь от действий.

Сохрани semantic tokens и плотность действующей дизайн-системы. UI/UX Pro Max используй как справочник, `frontend-design` — при запросе выразительного визуального направления. Не генерируй новую тему вместо существующей. Для сложного компонентного API подключай `vercel-composition-patterns`, без рефакторинга вне задачи.

Проверь зависимые компоненты, Query-cache и URL; соблюдай независимость хранилищ. Права определяй permission/scope/статусом. Добавь релевантные loading/empty/error/forbidden/read-only состояния, keyboard/focus/reduced-motion и готовность RU/KZ/EN. Не подключай production API, backend, новые библиотеки или инфраструктуру без необходимости и соответствующего запроса.

## Проверить и передать

1. Выполни проверки затронутого приложения из AGENTS.md, затем `prototype-flow-qa` для реализованного сценария; при доступности используй официальный `playwright`.
2. Обнови screen catalog при изменении экранов, module/flows при изменении переходов, open questions для нерешённых решений и implementation status после milestone.
3. Для отдельного запроса передачи утверждённого решения подключи `handoff-to-dev`; не выдумывай backend-контракты или согласования.
4. Перед завершением сопоставь результат с запросом и фактическими проверками (`verification-before-completion`). По-русски сообщи изменение поведения, причину выбора, допущения, открытые вопросы и ограничения проверки. Не выдавай гипотезу или непроверенный flow за завершённое решение.
