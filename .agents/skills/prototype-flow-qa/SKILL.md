# Prototype Flow QA

Подтверди работоспособность затронутого пользовательского сценария и составь приоритетный список воспроизводимых проблем. Этот skill проверяет связность прототипа; для отдельного эвристического аудита используй `ux-heuristics-audit`/`web-design-guidelines`.

## Определить область и ожидания

1. Из корня проекта прочитай AGENTS.md, обязательные документы и task-specific ссылки из `docs/README.md`, если они ещё не прочитаны. `archive/` исключён из normal QA.
2. Установи изменённый flow, route/entry point, synthetic fixture, permission/scope/статус, предусловия и ожидаемый исход. Используй актуальные docs и код; различай дефект, документированную заглушку, гипотезу и открытое требование.
3. Для БГД учитывай IndexedDB и текущие значения без версионности; для автономной интерпретации — отдельный localStorage namespace; для справочников — независимые связи/ревизии. Скрытый route интерпретации не объявляй рабочим публичным экраном.
4. Ограничь проверки затронутым сценарием и его зависимостями. Не запускай полный аудит продукта для небольшой правки. Не исправляй функциональность в задаче на аудит без соответствующего запроса.

## Проверить переходы и контекст

Проследи вход → выбор → действие → результат → возврат, включая прямую ссылку, reload, Back/Forward, смену объекта/раздела/вкладки и отказ от несохранённого черновика, где применимо.

Сверь URL, заголовки, выбранную строку, боковую панель, редактор, график/карту и вычисляемые итоги: все должны относиться к одному объекту и актуальному состоянию. Проверь, что фильтр или смена родителя не оставляют устаревшую дочернюю выборку.

## Проверить операции и данные

- Таблица: поиск, сочетание фильтров, сброс, сортировка/выбор/пагинация, массовое действие — только если они представлены в UI; сопоставь отображаемые итоги с synthetic-набором.
- Форма: корректный и некорректный ввод, обязательные поля, диапазоны/связи, дубликат, сохранение, отмена, повторное открытие/reload. Ошибка не должна уничтожать введённое.
- Кнопки/меню/диалоги: наблюдаемый отклик, закрытие/Escape, фокус и его возврат, disabled/pending/read-only. Выявляй noop-кнопки и «успех» без изменения данных. Документированное ограничение оценивай по тому, понятно ли оно пользователю.
- Mock-данные: стабильные ID, согласованные связи и единицы, отсутствие случайных значений в повторяемом сценарии, независимость namespace и корректное обновление Query-cache.
- Состояния: relevant loading, empty, no filter results, error/retry, forbidden, read-only, invalid URL и несохранённые изменения. Не добавляй скрытые продуктовые переключатели лишь ради QA; используй существующие fixtures/permissions или компонентную проверку.

## Выполнить проверки

Запусти соответствующие команды AGENTS.md и проверь exit codes. Для frontend-изменений основного приложения это typecheck/test/lint/build; для атласа используй его отдельный package.json.

Для браузера прочитай официальный `playwright`. В Windows обёртка `.agents/skills/playwright/scripts/playwright_cli.ps1` запускает закреплённый CLI через npx; для Bash доступен исходный `.sh`. Не используй глобальный путь upstream и не меняй HOME/CODEX_HOME. Браузер запускай в отдельной именованной сессии без пользовательского профиля. Используй `.tmp/design-qa/` для snapshots/screenshots/traces и явную конфигурацию CLI при необходимости.

Перед click/fill используй свежий snapshot; после смены экрана, раскрытия меню/диалога и заметного изменения DOM получай новый. Не угадывай element refs. Предпочитай реальные действия CLI; evaluate используй только для необходимой диагностики. Сброс demo-данных допускай только в своей изолированной QA-сессии. Закрой созданную сессию по окончании, не закрывай чужие браузеры или серверы.

Выполни happy path и значимые ветви отказа. Сними затронутую рабочую область на desktop и узком viewport, проверь визуально и по поведению: читаемость, плотность, обрезание, overflow, focus, non-color markers, модальные слои и согласованность с tokens. Проверь console errors; отделяй ранее существовавшие сообщения от регрессий.

Если браузер или сеть недоступны, продолжи статические/компонентные проверки и явно укажи непроверенные потоки. Сборка и screenshots сами по себе не доказывают корректность взаимодействий.

## Оформить результат

Для проблемы запиши: **приоритет | route/fixture/permission | шаги | ожидалось | фактически | последствие | доказательство | рекомендуемое исправление**.

- P0: критическая потеря/смешение данных или доступ вопреки ограничениям, блокирующие демонстрацию.
- P1: основной сценарий не завершается, неверный объект или результат, необратимая потеря черновика.
- P2: нарушена вторичная ветвь, восстановление, keyboard/focus, адаптивность или заметная визуальная согласованность.
- P3: небольшая ясность текста или визуальный дефект без блокировки задачи.

Оценивай приоритет по реальному воздействию; объединяй повторения одной причины. Отдельно сообщи документированные ограничения и вопросы, не выдавая их за регрессии. Заверши кратким отчётом: команды и исходы, проверенные flows/viewports, дефекты и непроверенные области. Используй `verification-before-completion`; не обещай полноту QA без доказательств.
