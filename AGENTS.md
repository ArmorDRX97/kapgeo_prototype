# KAPGEO — контекст проекта для Codex

## Что мы создаём

KAPGEO — кликабельный дизайн-прототип будущей информационной системы. Мы проектируем интерфейс непосредственно в React: создаём экраны, поля, таблицы, графики, навигацию и интерактивное поведение в коде, как при работе над макетами и прототипом в Figma, но сразу на выбранном frontend-стеке.

У работы три результата:

- **Дизайн:** наглядно показать, как будет выглядеть продукт.
- **UX-прототип:** дать пройти пользовательский сценарий и увидеть, что происходит при переходах, вводе данных, выборе объектов и управлении графиками.
- **Основа для разработки:** передать команде React-компоненты, стили, структуру экранов и реализованные взаимодействия на технологиях проекта.

Качество оценивается по ясности интерфейса, удобству сценариев, убедительности демонстрации и пригодности кода для дальнейшей работы. Передача frontend-наработки не означает, что система готова к промышленной эксплуатации.

## Границы прототипа

Все рабочие данные — вымышленные демонстрационные примеры. Допустимы статические массивы, заранее подготовленные результаты, повторяющиеся записи и локальная генерация. Достаточно, чтобы данные подходили экрану и позволяли оценить его поведение; полнота и достоверность реальной базы здесь не являются целью.

Backend, подключения к реальным API, реальные базы данных и интеграции в рамках обычных задач не разрабатываются. Не добавляй их без отдельного запроса. Имитации авторизации, прав, расчётов, фоновых задач и сохранения служат демонстрации интерфейса и не подтверждают наличие соответствующей серверной функции.

Модули могут намеренно использовать независимые наборы данных, даже если в будущем продукте они будут связаны. **Не строй сквозную модель данных, синхронизацию модулей, каскадные обновления или сложные предметные зависимости только ради реалистичности.** Создавай связь лишь тогда, когда она нужна для явно поставленного демонстрационного сценария, и в минимальном достаточном объёме.

Внутри показанного сценария взаимодействие должно быть понятным и согласованным: выбор выделяет объект, фильтр меняет выдачу, кнопка открывает нужный экран или диалог, изменение настройки графика отражается на графике. Сохранение может обновлять только локальное состояние. Для расчёта допустим заранее подготовленный результат. Если действие ещё не проработано, обозначь это понятной заглушкой; не показывай ложное подтверждение выполненной операции.

Уже существующие IndexedDB, localStorage, sessionStorage и mock-репозитории — средства локальной имитации. Не расширяй их до инфраструктуры реального продукта и не удаляй работающий механизм без необходимости для задачи. Не выдавай демонстрационные формулы и придуманные ограничения за утверждённые бизнес-правила.

## Как принимать решения

Используй профессиональное суждение в дизайне, UX и React-разработке. Самостоятельно выбирай способ решения и глубину проработки, соразмерные задаче. Здесь не требуется следовать обязательному набору ролей, этапов, сторонних методологий или скачанных skills.

Опирайся на текущую задачу пользователя, принятые проектные решения и существующий интерфейс. Изучай относящиеся к изменению код и материалы по необходимости. Новые явные решения пользователя имеют приоритет над старыми описаниями; существующая реализация показывает текущее поведение, но сама по себе не делает его правильным.

Если можно продолжить с разумным обратимым допущением — продолжай и кратко обозначь его, когда оно существенно. Уточняй только то, без чего можно заметно исказить замысел. Не придумывай требования и согласования. Не расширяй задачу до разработки соседних модулей или подготовки полноценной системы.

Устаревшая ссылка или отсутствующий документ не требуют восстанавливать прежний процесс. Не ищи и не переустанавливай удалённые проектные skills без запроса. Существенные новые решения фиксируй кратко в актуальном документе затронутой области, если такой есть; отдельная спецификация для каждой правки не нужна.

Исторический `archive/`, если он присутствует, исключай из общих поисков и обходов. Не читай, не индексируй и не меняй его по умолчанию. Обращайся только к конкретному архивному файлу по явному запросу пользователя.

## Технологии и устройство

Точный состав и версии зависимостей смотри в `package.json` и lock-файле. Текущая основа:

| Область | Технологии |
| --- | --- |
| Приложение | React 19, React DOM, TypeScript со строгой проверкой, Vite |
| Навигация и локальная работа с данными | TanStack Router, TanStack Query |
| Схемы и валидация | Zod |
| Интерфейс | общие компоненты `src/shared/ui/`, CSS и токены `src/app/styles/`, иконки Lucide |
| Геологическая визуализация | локальный пакет `@kapgeo/geo-viz` в `packages/geo-viz/`, Canvas и d3-scale; polygon-clipping для геометрии |
| Внутренняя карта знаний | React Flow (`@xyflow/react`), ELK (`elkjs`), html-to-image, Tailwind CSS 4 |
| Проверки | TypeScript, ESLint, Vitest, Testing Library, jsdom; MSW для имитации запросов там, где он используется |

Основное приложение организовано в `src/app`, `src/pages`, `src/features`, `src/entities`, `src/shared`; локальные данные обслуживает `src/repository`. Сохраняй существующие границы и направление зависимостей от композиции приложения к общим компонентам. Не вводи новые архитектурные слои ради формального соответствия шаблону.

Карта знаний находится в `src/internal/knowledge-map/` с отдельным HTML-входом `internal/knowledge-map.html`. Это внутренний инструмент команды с собственным оформлением и изоляцией в iframe. Её библиотеки и стили не задают дизайн основного приложения. Подробности переноса и границ описаны в её локальном `README.md`.

Используй выбранный стек и доступные инструменты там, где они помогают задаче. Новую зависимость добавляй при конкретной необходимости; не заменяй существующий подход только из-за личного предпочтения. Подготовка к передаче разработчикам означает понятные компоненты, явные состояния и отделимые mock-данные, без спекулятивных API-контрактов и инфраструктуры «на будущее».

## Качество интерфейса

Развивай существующий визуальный язык KAPGEO: общие компоненты, семантические токены, типографику, плотность и паттерны рабочих областей. Не меняй тему, палитру или библиотеку интерфейса без задачи на такой пересмотр.

Прорабатывай значимые для сценария состояния и обратную связь: выбор, фокус, недоступность действия, ввод, результат, пустая выдача или ошибка. Не нужно искусственно реализовывать все возможные серверные состояния на каждом экране. Демонстрационные данные и упрощённая логика не оправдывают сломанную навигацию, неработающие элементы или неудобный интерфейс.

Сохраняй нужный пользователю контекст при переходах и возврате. Учитывай прямой вход, перезагрузку и историю браузера там, где они затронуты задачей. Для интерактивных таблиц, карт и графиков важны удобство управления, читаемость и отзывчивость. Поддерживай клавиатуру, видимый фокус, понятные подписи и компоновку на подходящих для рабочего экрана размерах. Учитывай готовность интерфейса к RU/KZ/EN, не усложняя локализацию без текущей потребности.

## Проверка и передача результата

Команды запускаются из корня проекта:

```text
npm run dev        # http://127.0.0.1:4173
npm run typecheck
npm run test
npm run lint
npm run build
npm run preview    # http://127.0.0.1:4173/kapgeo_prototype/
```

Общая сборка также проверяет данные и изоляцию встроенной карты знаний; отдельный запуск из прежней папки атласа не нужен.

После изменений frontend-кода выполняй typecheck, test, lint и build. При изменении поведения добавляй проверки там, где они помогают защитить сценарий; не создавай тестовую инфраструктуру ради разовой демонстрации. Для изменений только документации достаточно проверки содержания, ссылок и diff.

Изменённый UX проверяй в доступном браузере: видимый результат действий, переходы, затронутые состояния и компоновку. Для визуальных изменений оцени сам экран. Если браузерная проверка недоступна, прямо сообщи об этом; успешная сборка не подтверждает качество UX.

Общайся по-русски. В результате кратко объясняй, что изменилось, как это работает в демонстрации, какие упрощения существенны и что фактически проверено. Не заявляй о готовности реальной интеграции или бизнес-функции на основании mock-поведения.

Сохраняй пользовательские изменения. Не выполняй Git-коммит, деплой или публикацию без отдельной просьбы.
