## Пользовательский результат

Геолог или интерпретатор открывает скважину из БГД, сопоставляет исходную литологию/керн/пробы с каротажами на общей шкале глубины, размечает литологию и проницаемость, привязывает керн к каротажу, проверяет изменения и сохраняет связанный результат. После reload результат доступен в интерпретаторе и соответствующих представлениях БГД.

## Конкретные ограничения текущего кода

1. `LogCurve` содержит описание кривой, но не точки. `LogCurvePreview` рисует четыре заранее заданных path, независимо от значений измерений. Из этой картинки нельзя получить достоверное КС-разбиение или среднее КС.
2. БГД-литология меняет массивы непосредственно. Общий interval engine есть, но этот редактор использует из него validation/diff, а не все команды. Generic `add/update/stretch` не выполняет legacy-overwrite/каскадный перенос связанных объектов.
3. Добавление литологии сейчас только в первый незаполненный gap; split только по середине; merge сохраняет свойства выбранного интервала и склеивает описания, даже если породы различаются. Это не правила графического редактора 1.24.
4. `mineralization?: string` и одиночный select не моделируют набор минерализаций из РП. Цвет сейчас доступен для всех трёх track; по 1.12 цвет предназначен для керна/сводной, по 1.26 у бескернового цвет отсутствует.
5. `CoreRun` хранит одну пару глубин и выход; не хранит соответствие и рассчитанные глубины/выход по сводной колонке. `adjustedDepth*` проб — ручные поля, а не результат общего преобразования.
6. Seed керновых рейсов и литологии независим: для WELL-1042 два рейса начинаются на 112,4 м, суммарно занимают 8 м с неполным выходом; керновая литология содержит разности по почти всему стволу и не ограничена этими рейсами. Проверка 1.26 такой набор не пропустит. Нужен согласованный fixture, а не отключение проверки.
7. Есть два семейства данных проб: `WellCoreWorkspace.samples` рабочего БГД и `WellGeologyWorkspace.samples/granulometry/labResults` другого seed/API-контура. Не строить интерпретатор на втором наборе, обходя реальные БГД-пробы. Назначить один источник по каждому предметному виду.
8. `sampleType: Керновая/Контрольная/Дубликат` не совпадает с четырьмя видами материала КП/ГС/ЛГХ/ТП. Нужны независимые поля «вид исследования/материала» и «тип контроля» либо явно согласованная модель.
9. Основной каротаж сейчас выбирается целым набором: `setPrimary` снимает флаг со всех остальных наборов. Legacy описывает основной промер по каждому типу каротажа. Для ближайшего среза достаточно явного выбора набора и канала КС; не делать скрытую замену всей логики БГД.
10. `GeologyNavigator` извлекает месторождение регулярным выражением только из `/geology/bgd/...`. При новом route нужно расширить общий context resolver и переходы.
11. Наличие `stratigraphy`, `GranulometryRun`, `mainCurve`, `published`, артефактов или jobs в моделях не подтверждает законченного UI или настоящего расчёта. Отдельного кернового интерпретатора, КС-расчётчика и карты глубин в текущем route tree нет.

## Предлагаемый UX

Отдельная рабочая область в существующем модуле «Геология». БГД остаётся местом исходного ввода и просмотра данных; интерпретация пользуется теми же объектами.

Предложение маршрута: `/geology/interpretation/:depositId/wells/:wellId?view=lithology|technology|core&track=core|log|composite&from=...&to=...&selection=...`. Это проект маршрута, не существующий deep link. Параметры track применяются только к литологии; недопустимые значения нормализуются.

- Постоянный выбор месторождения/скважины с переиспользованием контекстной панели. В карточке БГД — переход «Открыть интерпретацию» с сохранением контекста.
- Заголовок: скважина, диапазон, версия результата, вид работы, явный synthetic/demo-признак, состояние исходных данных.
- Центр: синхронные колонки по общей глубине; слева исходные данные, рядом результат и каротажи. Нельзя увеличивать высоту тонкого интервала так, чтобы его положение переставало соответствовать шкале, как сейчас у упрощённой колонки.
- Панель команд: выбор/новый интервал/контакт, split/merge/delete, undo/redo; разрешённые команды зависят от выбранного объекта и режима.
- Панель свойств выбранного интервала: точный численный ввод, источники, связанные рейсы/пробы, ошибки. Контекстное меню дополняет, а не заменяет доступные кнопки/keyboard-команды.
- Настройки общие: диапазон/масштаб/шаг глубины, показать/скрыть/переупорядочить/изменить ширину колонок, шкалы и выбранные каротажи. Физические сантиметры desktop-чертежа адаптировать к web, не копировать буквально.
- Нижняя область: изменения, проверки, «Сохранить»/«Отменить изменения». Preview КС применяется в черновик, затем отдельно сохраняется.
- Unsaved changes при уходе/смене скважины: сохранить, отбросить, остаться. На телефоне — сохранение масштаба глубины и горизонтальная прокрутка колонок; точные операции доступны в форме.

## Порядок реализации по завершённым срезам

### Срез 0. Подготовить согласованные входы

- Один детерминированный fixture демонстрационной скважины: 2–3 рейса с потерями керна, литология строго по поднятому керну, промер с известным шагом и null, составная проба, численные КС/ГК.
- Дополнительные fixtures: нет КС, ошибка литологии/выхода, проба в бескерновой части, устаревшее соответствие.
- Зафиксировать, откуда читаются каждый вид проб/литологии/измерений; не уничтожать пользовательские IndexedDB-изменения. Если нужна миграция seed — версионировать и применять только к нетронутым synthetic-записям либо отдельной новой demo-скважине.
- Результат: выбранная скважина проходит исходную проверку, кривая рисуется по тем же числам, которые идут в расчёт.

### Срез 1. Общая рабочая область + п. 1.24

- Route, permission/scope, loading/empty/error/not-found/read-only.
- Общая шкала, выбранные каротажи, свойства/контакты, overwrite/trim/split/auto-merge, диапазонное удаление, undo/redo.
- Проверка керновой литологии по рейсам/выходу/цвету; набор минерализаций.
- Сохранение существующих track в БГД без второго независимого хранилища.
- Результат: пользователь изменил границу на фоне КС/ГК, сохранил, открыл БГД и увидел те же интервалы после reload.

### Срез 2. П. 1.25

- Новый технологический workspace и бинарная колонка, ручной ввод/контакт/удаление.
- «Разбиение по КС»: выбор источника, диапазон, методы потенциал-/градиент-зонда, направление, порог, округление, минимальные мощности и продолжение проницаемого.
- Реальный детерминированный demo-расчёт по точкам, редактирование preview, пометка устаревшего preview после изменения параметров, просмотр последствий замены, apply/cancel, undo и сохранение.
- Для неполных/невалидных данных — сообщение и отсутствие притворного результата. Сохранять входные версии, выбранный канал, параметры и происхождение автоматических/ручных изменений.
- Результат: изменение порога меняет интервалы; «Отмена» не меняет черновик; применённые интервалы сохраняются.

### Срез 3. П. 1.26: связанная привязка керна

- Модель соответствия диапазонов с исходными ID, диапазонами по бурению/сводной, ориентацией, типом `core/no-core`, принадлежностью рейсу и связанными ID.
- Проверка входов; тождественная инициализация; конфликт с изменившимися входами и явный reset/rebuild.
- Операции рейсов и сегментов из требований, с переносом всех дочерних данных в одной команде; расчёт сводных рейсов, восстановление нулевых сегментов, проверка merge и промера.
- Использовать сводный track как представление связанного результата; не сохранять несогласованные mapping и литологию.
- Первое демонстрируемое ядро может использовать КП, но тогда п. 1.26 обозначается как частично выполненный. Для заявления полного покрытия РП нужны также ГС/ЛГХ/ТП и их сводные интервалы.
- Средний КС по литологии по каротажу, свойства/восстановление источника, реестр проб, прямой/обратный расчёт глубин.
- Результат: сдвиг/переворот керна переносит литологию, промер и все части проб; исходная колонка остаётся доступной для сравнения, сохранение переживает reload.

## Техническая модель: минимум, который нужен

Предлагаемые сущности, названия уточняются при кодировании:

- `LogCurveSamples`: канал/набор, единицы, отсортированные точки, null/gaps, версия. КС=RES в demo-каталоге.
- `TechnologyInterpretation`: скважина, бинарные интервалы, параметры/метод/диапазон расчёта, версии входов, provenance, версия результата.
- `CoreDepthMapping`: сегменты исходной/сводной глубины, orientation, runId, связи с литологией/промером/пробами, признак вставленного/нулевого сегмента, версии источников.
- Derived-view сводных рейсов/литологии/промера/проб, построенное через mapping. При persistence нельзя сначала записать одну часть и оставить остальные несогласованными при ошибке.

При перестановке/перевороте нужна карта из нескольких сегментов, а не один общий offset. После split одна проба может иметь несколько результирующих диапазонов с тем же sampleId и неизменными лабораторными результатами. Для добавленного бескернового сегмента обратного соответствия может не быть. В такой участок нельзя помещать отбор керновой пробы.

Generic interval engine переиспользовать для сортировки, snapping, diff и части команд. Overwrite, каскадный перенос, ориентация, нулевые/восстанавливаемые сегменты и связанные данные требуют отдельной предметной политики/команд и тестов. Undo в керновом режиме должно охватывать весь связанный результат, а не только один массив.

Новые domain types — `entities`; команды/сценарии — `features/interpretation`; route-композиция — `pages/geology`; общий рисунок/панель — переиспользуемый workbench (при необходимости `widgets`); IndexedDB-adapter — `repository/demo`; базовые depth/interval utilities — `shared`. Компоненты страницы не импортируются обратно в features/widgets.

## Что не входит автоматически

Промышленный backend/ACL/ЭЦП, произвольные LAS/другие файлы, реальные данные, AI-классификация, геотехнологические разрезы, запасы, 2D/3D, полный печатный паспорт и Office-экспорт. Источники у новых demo-расчётов и ручных изменений явно обозначаются. Автономные административные справочники не подключать к БГД/интерпретации без нового решения по OQ-ADM-04.

Новый workflow утверждения не вводится только потому, что есть сводный результат. Если он потребуется, отдельно определить роли/статусы и обновить продуктовую документацию.

## Открытые решения

Записаны также в `docs/ui-ux/11-traceability-open-questions.md` как OQ-INT-01…06:

1. Полное покрытие четырёх видов проб в ближайшем релизе или последовательные срезы с честной пометкой частичного 1.26.
2. Окончательная методика двух КС-алгоритмов: равенство порогу, интерполяция, плато/шум/null, крайние тонкие интервалы, округление и средний КС.
3. Сохраняется ли ограничение мощности сегмента с промером «исходная / 0,1 м / 0»; как трактовать масштабирование связанных интервалов.
4. Права геолога/геофизика на виды интерпретации, object scope, редактируемость сохранённого результата; нужен ли approval.
5. Единый источник по четырём видам проб и сводным данным; при изменении исходных записей — rebuild/миграция/reset и правила совместного редактирования сводного track.
6. Крайние случаи interval overwrite/delete, равенство свойств для auto-merge, разрешённый итоговый диапазон при сдвиге/расширении сводной колонки.

Эти вопросы не мешают начать общий workbench и согласованный fixture. Допущения будущего demo-расчёта должны быть записаны явно; не считать их утверждённой промышленной методикой.
