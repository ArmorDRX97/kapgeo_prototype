## Вывод

Текущего набора зависимостей достаточно для первого полного пользовательского среза интерпретации. Центральная основа — существующий собственный Canvas 2D-планшет `@kapgeo/geo-viz/wellog` и `d3-scale`; локальный черновик — Zustand + immer + zundo; формы/проверки — React Hook Form + Zod; данные — orval/TanStack Query, в демонстрации MSW.

Основной недостающий объём — предметная модель и команды, интервальные треки, согласованное редактирование керна/литологии/проб и API-контракты. Наличие библиотеки не означает, что эти сценарии уже реализованы. Новую библиотеку графиков, движок drag-and-drop или WebGL для начального среза подключать не требуется.

|---|---|---|

| Планшет, общая шкала, кривые | `@kapgeo/geo-viz/wellog`, Canvas 2D, `d3-scale` | Расширить существующий планшет интервальными треками. Canvas — браузерный API, не новая npm-зависимость |
| Панели, формы, действия, справочники | `@kapgeo/ui`, shadcn/Radix, Tailwind, lucide | Переиспользовать компоненты и семантические/предметные токены. shadcn — исходники пакета ui, не отдельный установленный UI-kit |

| Локальный черновик | `zustand`, `immer` | Модель редактируемого результата, выбранный инструмент, preview. Не дублировать серверную БГД в глобальном store |
| Undo/redo | `zundo` | Единая история предметных команд: один завершённый drag — один шаг; перенос керна и всех зависимых данных — один шаг. Исключить hover, zoom, pan, selection и исходные точки каротажа |
| Серверные данные и сохранение | `@kapgeo/api`, orval, `@tanstack/react-query` | Генерируемые DTO/хуки, согласование контракта, сохранение/версия результата, обновление запросов после mutation. Query-cache не является историей редактора |
| Демонстрационные данные | `msw` | Детерминированные численные каротажи и согласованные рейсы/пробы, mock preview/сохранения и ошибки. В основном фронтенде demo-расчёты за mock API, не внутри UI |
| Реестр интервалов и проб | `@tanstack/react-table`, `@tanstack/react-virtual` | Таблицы, сортировка/фильтры, виртуализация длинных списков. Они не рисуют кривые и не реализуют правила split/merge |
| Доступ | `@kapgeo/auth`, Keycloak, CASL | Permission + объект/область + статус. Редактирование, расчёт, применение и просмотр результата проверяются явно |
| RU/KZ/EN | i18next и связанные пакеты | Параметры, единицы, ошибки, provenance и названия инструментов; основной frontend использует locale `kk` для казахского |
| Статусы и сбои | sonner, react-error-boundary | Уведомления об операциях и изоляция ошибок UI. Ошибка валидации остаётся возле соответствующего поля/результата |
| План месторождения, пространственный контекст | `@kapgeo/geo-viz/plan`, `ol`, `proj4` | Нужны для планов и географических координат. Вертикальная глубина и соответствие бурение↔сводная — другая предметная задача |
| Даты, классы, стили, анимации | date-fns, cva/clsx/tailwind-merge, tw-animate-css | Вспомогательный слой. Не являются ядром интерпретации; анимации учитывать вместе с reduced motion |
| Проверки и сборка | Vitest, Testing Library, TypeScript, ESLint, Vite/Turbo | Предметные команды, связность результата, события Canvas, права и маршруты; существующие инструменты достаточны |

Виртуализация списков и Canvas с прореживанием кривых решают разные задачи. TanStack Virtual предоставляет headless-виртуализацию, UI и взаимодействия остаются приложению: [официальная документация](https://tanstack.com/virtual/latest/docs/introduction).

## Что уже есть в geo-viz и БГД

Проверены `packages/geo-viz/src/wellog/{types,index,well-log,draw-track,depth-scale,decimate,sample}.ts[x]`, `apps/web/src/modules/geology/model/well-log.ts`, компоненты `well-log-panel.tsx` и `bgd-log-viewer.tsx`.

- Публичный импорт — **`@kapgeo/geo-viz/wellog`** (именно `wellog`). Пакет также экспортирует `/plan`, `/coords`, CSS плана. Интервального или разрезного редактора среди этих экспортов пока нет.
- `WellLog` рисует кривые и общую ось глубины на Canvas; реагирует на размер контейнера и DPR; поддерживает wheel zoom, drag pan, crosshair и считывание значений.
- `depthRange` можно контролировать снаружи через `onDepthRangeChange`. Это пригодно для общей глубины нескольких треков.
- `TrackSpec` сейчас содержит `curves: CurveSpec[]`, заголовок, ширину и grid. Нет отдельного вида литологического/кернового трека, interval selection, mode/tool и edit callbacks.
- `CurveSamples` — **два параллельных массива** `depths` и `values`, допускающие `Float64Array`; глубины возрастают, пропуски значений обозначаются `NaN`. Это точнее описания «плоские пары» в ADR/старых справочных инструкциях.
- Адаптер `toCurveSamples` строит глубины из `depthFrom + i * step` и переводит отсутствующие значения в `NaN`; основной frontend уже имеет численные кривые. Для нерегулярного шага потребуется явный контракт массива глубин.
- В основном frontend КС обозначен **`RS`**, в прототипе — `RES`; каверномер также требует проверки соответствия `CAL`/`CALI`. Сопоставление делать явно, не по похожему имени.
- Шкала глубины уже использует `d3-scale/scaleLinear`. Горизонтальная линейная/логарифмическая шкала реализована в `valueToX`; не требуется переписывать её ради использования `scaleLog`.
- Публичные помощники включают `createDepthScale`, `visibleWindow`, `clampRange`, `niceTicks`, `decimate`, `findSampleIndex`, `valueAtDepth`, `drawTrack`, `valueToX`, `visibleIndexRange`, `drawDepthAxis`.
- БГД уже использует этот Canvas через `BgdLogViewer`, с `useGetWellLogs(wellId, {runId})` и адаптером `toTracks`. Замена фиксированного SVG нужна прототипу, а в основном приложении задача состоит в расширении работающего планшета.
- `createBgdWorkspaceStore` уже использует Zustand vanilla + `temporal` из zundo с лимитом 40. `GeologyStore` хранит окно глубины отдельно. Это хорошая основа, но не готовая история связанных операций интерпретации; применение immer в этих двух store не обнаружено.
- Литология основного БГД в `bgd-lithology.tsx` пока представлена списком кнопок и формой; Canvas-кривая в соседнем сценарии ещё не означает, что литологию можно редактировать прямо на планшете.

Преобразование метры↔пиксели через шкалу необходимо для выбора границ: `scaleLinear` поддерживает обратное преобразование `invert`. Логарифмическая шкала требует области, не пересекающей ноль. Эти функции описаны в документации [linear](https://d3js.org/d3-scale/linear) и [log](https://d3js.org/d3-scale/log); они не реализуют геологическое соответствие переставленных/перевёрнутых сегментов.

`zundo` предоставляет историю состояния и настройки вроде `partialize`/`limit`; состав истории и атомарность предметной команды определяет приложение. Основание: ADR 0007 и [документация zundo](https://github.com/charkour/zundo). Нельзя помещать исходные длинные кривые в каждый history snapshot.

## Ограничения существующего планшета, которые проверить до редактора

1. **События редактирования и панорамирования.** Сейчас `pointerdown` тела планшета запускает pan и pointer capture. Выбор двух точек/drag контакта требует согласованных режимов и отмены жеста. Независимый overlay, конкурирующий за pointer events, не является достаточной интеграцией.
2. **Пропуски после прореживания.** В длинном пути `decimate` пропускает `NaN`; полностью пустой bucket также пропускается. `drawCurve` разрывает линию только при встретившемся невалидном значении. Поэтому после decimation разрыв может исчезнуть и соседние валидные участки могут соединиться. Это вывод по коду, не результат browser smoke. Нужны сохранение границ пропусков и тест длинной кривой с gap.
3. **Расчёт по полным данным.** Min/max decimation предназначена для отрисовки. Пороговый расчёт интервалов и средний КС нельзя выполнять по прореженному отображаемому массиву. Использовать исходные точки и согласованные правила работы с пропусками.
4. **Шкала и точность.** Проверить пустые/постоянные кривые, невалидные диапазоны, нулевые/отрицательные значения КС, единицы и округление контактов. Пиксельный clamp графика не должен подменять сохранённое измерение.
5. **Тематические и текстовые представления.** Добавить заливки/штриховки и легенду через токены; выбор и точное изменение доступны с клавиатуры и через форму/таблицу. Canvas сам по себе не даёт доступной структуры интервалов.
6. **Печать.** ADR 0006 предусматривает отдельный SVG-рендерер общей геометрии; существующий публичный API планшета не подтверждает реализацию печати. Экспорт в масштаб/A0 — отдельный этап; растровый screenshot Canvas не закрывает это требование.

## Где выполнять расчёт и хранить результат

В основном фронтенде промышленный расчёт по КС, преобразование глубин и согласованное сохранение должны идти через gateway/backend, согласно его архитектурным инструкциям и ADR 0013. UI хранит черновик/предпросмотр, отправляет параметры/команды, показывает результат и последствия применения. В демонстрации соответствующую семантику воспроизводит MSW; чистые функции можно покрыть тестами вне компонентов.

До реализации согласовать контракт: источник и версия кривой, система глубины, параметры/метод, версия входов и результата, сегменты mapping, связанные изменения проб/промера/литологии, ошибки и конфликт версии. Наличие orval не создаёт отсутствующий endpoint. После сохранения обновлять все затронутые запросы, чтобы БГД и интерпретатор показывали один результат.

Для локальных жестов допускается немедленный preview; его математическая и предметная семантика должна соответствовать серверному контракту. Разрешение открытых вопросов алгоритма в прототипе считается demo-допущением, не утверждённым промышленным методом.

## Карты и последующие задачи геологии

- `ol` уже используется в плане месторождения. `proj4` объявлен в geo-viz, но это не доказательство использования конкретной проекции в текущем плане: поиск по исходникам пакета не обнаружил его импорта.
- План работает с локальной метрической проекцией `KAPGEO:PLAN`; преобразование порядка геологических X/Y выполнять существующими coords-помощниками. Привязка керна по глубине не является географической проекцией.
- Для разрезов и корреляции можно расширить Canvas/SVG и переиспользовать шкалы/треки. Готового разрезного редактора в проверенных экспортах нет.
- Требования главы 4/5 по объёмным моделям не закрываются наличием OpenLayers или d3-scale. Решение о 3D-стеке требует отдельной задачи; для пп. 1.24–1.26 такая зависимость не нужна.
- `d3-shape` упомянут в ADR как возможная помощь SVG-варианту, но в проверенном `packages/geo-viz/package.json` не объявлен. Не записывать его в установленный стек и не добавлять до конкретной необходимости.
