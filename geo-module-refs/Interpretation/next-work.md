# Следующая работа: предложение, не начало реализации

13.10.2026. Пользователь поручил только исследование. Перечисленные этапы — рекомендуемый порядок после отдельной задачи на доработку интерпретации. Оценки сроков/трудозатрат и готовность промышленного расчёта не заявляются.

## Предлагаемый пользовательский сценарий

Выбрать скважину → выбрать запись/метод → видеть исходные кривые и связанные результаты на общей глубинной оси → настроить параметры → получить отдельный preview → проверить/исправить → применить в документ → сохранить → собрать паспорт/таблицы.

При отсутствии необходимых данных объяснять конкретную зависимость, например «Для обсыпки нужен фактический фильтр», сохраняя возможность просмотра КМр. Изменение шкалы/камера не меняют расчёт. Новая версия исходной записи или параметров делает зависимый результат устаревшим; пользователь принимает пересчёт явно. Ручная корректировка должна сохранять происхождение и возможность отмены.

Предлагаемая структура: общий контекст скважины/записей; общий планшет; переключатель методов; компактные настройки/свойства справа; таблица результатов по выбранному методу. Литология/керн/пробы сохраняются. Не копировать десятки отдельных окон EXE и clipboard-сценарий. Точное расположение вкладок и групп методов разработать в следующей UX-задаче с учётом ширины рабочего поля, не фиксировать десять одновременно видимых вкладок без проверки.

Нельзя обещать полное соответствие Альфе до уточнения методик. Сохранение ручных результатов и визуальная демонстрация возможны раньше автоматического промышленного расчёта. Новые автономные fixtures должны содержать характерные случаи: разная дискретизация, gaps, повторный каротаж, неоднозначная термоаномалия, несовпадение контроля, фильтр с несколькими секциями. Копирование реальных скважин из руководства не требуется.

## Будущая модель данных — направление

Нужны записи измерений (`curve + metadata + acquisition stage + provenance`) и результаты методов (`inputs/versions + parameters snapshot + result + manual corrections`). Единицы и диапазоны принадлежат конкретной записи/величине. Метод не определяется исключительно цветом или типом линии.

Литология, Кф/ЛФТ, интервалы руды, ЗПО, конструкция фильтра, цементация, металлические метки, секции РМ и пары контроля — отдельные предметные структуры. Изменение связанных результатов распространяется через явные зависимости. Конкретные TypeScript/Zod-схемы и миграции проектируются при реализации с сохранением существующих документов; новые backend-контракты сейчас не создаются.

## Критерии будущей приёмки

- У каждого действия наблюдаемый предметный результат, а не декоративная кнопка или скрытая запись в fixture.
- Идентичность скважины/записи/метода, глубина и единицы согласованы в URL, планшете, инспекторе и таблице.
- Исходные данные отделены от производных/ручных результатов; preview/Apply/Save/Undo и stale зависимостей проверены.
- Измеренные пропуски не интерполируются молча; отрицательные значения допускаются по смыслу метода, а не общим фильтром RS.
- Locked/permission/scope соблюдаются. Настройки просмотра доступны независимо от права изменения результата.
- Керн/пробы и старые сохранения не теряются при расширении модели; независимость от БГД/разрезов проверена.
- После реализации — typecheck/test/lint/build, UI-проверка desktop/mobile/keyboard, физический масштаб экспортного паспорта и независимые численные эталоны для заявленных расчётов.
